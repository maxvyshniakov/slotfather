# Scheduling

`grant()` runs in every client that looks at the queue (each waiting request, every few seconds, and each release), and it starts the waiting requests `plan()` picks:

1. Waiters are taken in arrival order, moved by their class (see Classes below); each that fits starts.
2. A waiting request that does not fit lets later requests that fit start first for `SLOTFATHER_OVERTAKE_WINDOW` seconds after it queued (600), as before.
3. The first waiting request past its window that does not fit is the **head**. Its start is reserved: the moment the held leases' expected ends free enough slots for it. A later request that fits starts before it only if three times (*safety*) its expected run ends by that moment and by the time the head will have waited its *limit* (2700 s), or if it takes only spare slots: those the head will not need at that moment even if the leases expected to run on past it are the largest ones (EASY backfill, made independent of which lease ends first). From the limit on nothing passes: the head holds everyone back as the window order did.
4. A waiting request whose client gives up first is no head (`run --wait`, the library's `acquire(wait=...)`, writes the moment on its entry as `until`): when it has not yet waited its limit and even the held leases' expected runs, taken without overrun, free its slots only after it gives up, it would leave without running, so the next waiting request past its window that does not fit is the head instead and requests that fit pass it. It keeps its head while any held lease's run is unknown (it may end any moment) or slots are held in an earlier queue, and from its limit on, as before; it still starts if its slots come free before it gives up. A lease back in the queue after a yield keeps its head whatever its first wait said. Older clients read past `until` and hold back for such a waiting request as before.

Expected runs come from `history.jsonl` (its last megabyte, read only when a request fits behind a head and kept in `estimates.json` beside it until the history changes, so other processes, releases and `available` read the small file; a file another version wrote is worked out again): the median of the last 20 released runs of the closest earlier kind of request, trying in turn the same label and command kind (`stats`' kind: program and first argument, with a runner's `run` target, a shell's `-c` command and no `env VAR=…`), the same label family (the label up to its ticket or agent id: `lane`, `post-merge`) and kind, that family with a check list of about the same size (`verify.sh --checks` of 128 to 255 checks), the kind under any label, about that size under any label, the same label, and the same family. Reaped leases and requests that gave up are left out: a reaped lease's time runs to whenever a look noticed its holder had died (an orphan of a hung CI job kept its slot for 2800 s), and one that gave up never ran. This leans the estimates short for a kind whose runs are often killed after real work (a CI job cancelled or timed out late in its run): only its runs that finished count. A request like nothing before counts as running the *fallback* (3600 s), so with the default limit it passes a head only into spare slots. A held lease past its expected run is expected to run on for the *overrun* share (half) of what it has run so far, because a run that overran its kind tends to be a long one.

`available` and `advise` answer for a request of unknown run (the fallback) unless given the command: `slotfather available --label L -- COMMAND...`, `slotfather advise [--max N] --label L -- COMMAND...`; `advise` reports the run it expected as `run_estimate` (`null`: unknown).

**Settings.** `slotfather order` shows the order and its numbers; `slotfather order backfill|window`, `--safety X` (at least 1), `--limit S` (0: no limit), `--fallback S`, `--overrun X`, and the classes' `--interactive S`, `--batch S` and `--yield-after S` (see below) save them for every client in `order.json` beside the queue, like `slots` saves capacity, and `slotfather order reset` restores the defaults. They take effect at the next look at the queue, also while it is busy. Every client's look grants for the whole queue, so a client's environment can only tighten them: `SLOTFATHER_QUEUE=window`, or a higher `SLOTFATHER_BACKFILL_SAFETY` or `_FALLBACK`, a lower `_OVERRUN` or a lower nonzero `_LIMIT`, a lower `SLOTFATHER_PRIORITY_INTERACTIVE` or `_BATCH` (classes move requests less), a higher `SLOTFATHER_YIELD_AFTER` or `0` (nobody is asked); looser values are ignored. A saved file that cannot be read gives the window order. The class knobs are written to `order.json` only when they differ from their defaults: a slotfather before them refuses a file with keys it does not know and falls back to the window order, and `slotfather order` says so when it saves one.

**When an estimate is wrong.** A request that runs longer than expected delays the head by the difference. The limit bounds it: no request passes a head after the limit, and none that is expected to end after it, so beyond the leases it waited for, the head waits only for the overrun of what passed it. An overestimate only keeps a request behind the head, as the window order did. The replays below with estimates halved, doubled and scattered (each one off by a random factor, e^N(0,1)) keep the longest wait of large requests at the current order's.

**Mixed versions.** Queue entries, `history.jsonl` and every output (`status`, `available`, `advise`, `slots`, `history`, the lease variables and nesting) are unchanged, so old and new clients share one queue. An older client grants by its own order whenever it looks, so until every client is updated the queue admits what either order allows: a new client's look starts a short request an old one would hold back, and an old client's look keeps today's behaviour for what the new order would refuse. Straylight's vendored `tools/slotfather` predates the history, so its runs are not in the estimates until it uses this one.

**Falling back.** `slotfather order window` restores the order before #643 for every client of this version at their next look, without classes or yield requests; `SLOTFATHER_QUEUE=window` does it for one client. `slotfather order --yield-after 0` keeps the classes and asks nobody to yield; `--interactive 0 --batch 0` keeps backfill without classes. Installing the previous version from a checkout of `bfa114b` (or `3e3a621`, backfill without classes) with `python3 install.py` also works; the queue and history need nothing.

### Classes

`run --class interactive|normal|batch` (the same as `--meta class=...`; the library's `acquire(meta={"class": ...})`) says how much someone waits for the request. **interactive** is work a person or agent waits on at once: a pre-push check, a single test. **batch** is work nobody waits on minute by minute: full gates, post-merge smokes, measurements (`-n all` gets no class of its own: say `--class batch`). Everything else, and every request that names no class, is **normal**.

The class moves where a waiting request stands in the order, by a fixed offset that is also its ageing: an interactive waiting request queues as if it came *interactive* seconds (1800) earlier, a batch one as if it came *batch* seconds (1800) later. So a batch request is ahead of every normal request that comes more than 30 minutes after it and of every interactive one that comes more than an hour after it; nothing waits behind newer work for longer than that. The window order (`slotfather order window`) has no classes.

Classes change only the order in which `plan()` takes the waiting requests; the window, the head and its reservation then work as before on that order, and the window and the limit count from when a request really queued. The head is the first waiting request in class order that is past its window and does not fit; a request that ranks ahead of it is not passing it, so the limit alone no longer bounds a head's wait. The bound becomes: a head starts by its limit plus the overrun of what passed it, or, if later, once every request that ranks ahead of it has run, and only requests that came within the class offsets after it can rank ahead (for a batch head, normal ones within *batch* seconds, interactive ones within *batch + interactive*: an hour). So a batch `-n all` measurement under a steady stream of interactive checks waits up to an hour plus the run of the last check that came within that hour, plus its overrun; the replay test has that trace. An interactive request that does not fit becomes the head in its turn and gets the head's reservation. A lease that yielded and does not fit becomes a head too; its limit counts from when it yielded.

### Polite preemption

A holder that opted in (`run --yieldable`, `acquire(..., yieldable=True)`) can be asked to give its slots back for a while; it is never stopped, killed or signalled, and a holder that did not opt in is never asked. An **interactive** waiting request asks when it has waited *yield_after* seconds (120), does not fit, and by the held leases' expected ends would not get its slots within another *yield_after*. It asks only yieldable holders of a lower class that have held their slots *yield_after* seconds since their last grant and have yielded fewer than two times; only as many as it needs (first those already asked, then batch before normal, then the one expected to run longest); and only when the queue would then start it, with the asked holders back among the waiting requests. Every look decides again: a request no longer needed (the waiting request started or left) is withdrawn.

The waiting request's own client may ask later or never (`SLOTFATHER_YIELD_AFTER`); that rides on its queue entry as `yield_after`, and every client's look decides yield requests by the saved settings and those entries alone, so clients with different environments do not write and withdraw each other's requests. A holder asked to yield checks once more that the waiting request would then start, and keeps its slots when it would not. The yield request is a file beside the holder's queue entry, `<entry>.yield`, whose path the lease's command gets in `SLOTFATHER_YIELD`; it holds `{"by", "label", "class", "count", "at"}` of the waiting request that asked. `slotfather yield` from inside the lease (the library's `lease.yield_slots()`) yields if asked and the waiting request still waits: the lease goes back to the queue (the same entry and holder, state `waiting`) just behind that waiting request, pinned there whatever its class (it is half done and holds its memory), the queue grants at once so the waiting request starts, and the command returns when the lease is granted again with its slots. Without a yield request it returns at once, saying `no yield requested`; it exits 0 either way. A nested `slotfather run` under a yielded lease waits until the lease is back. `status` shows `yieldable`, `asked-to-yield-for=LABEL` and `yielded=N`; `status --json` adds `class`, `yieldable`, `yields`, `yield_asked` (the request or `null`) and `position` (a waiting request's place in the order the queue serves); the dashboard's LANE DETAILS panel shows the request; `queue.log` records asks, withdrawals and yields. The history line of a lease that yielded carries `yields` and `yielded` (seconds back in the queue); its wait and run count from its first grant, and `stats` leaves the yielded time out of cores per slot.

#### What a client implements to be preemptible

Straylight's `tools/verify.py` and `tools/heavy.py` and Sid-Kit's `scripts/heavy.sh` and `scripts/verify.mjs` are the intended clients; they are not changed here.

1. **Opt in when taking the lease**: `slotfather run --yieldable --class batch ... -- COMMAND` (Sid-Kit's `heavy.sh`), or, for a client that holds its lease in-process (Straylight's `verify.py` through `tools/slot_lease.py`), `acquire(count, label, command, yieldable=True, meta={"class": "batch", ...})`.
2. **Look for a request between steps**, whenever a step ends and none of the lease's own work runs: Straylight between checks, Sid-Kit between `verify.mjs` steps. The look is one `stat`: `[ -e "$SLOTFATHER_YIELD" ]` in a shell, `os.path.exists(os.environ.get("SLOTFATHER_YIELD", ""))` in Python, `lease.yield_requested()` in-process. With parallel jobs (`--jobs N`), stop starting new steps once a request is seen and let the running ones finish first.
3. **Yield**: run `slotfather yield` (in-process `lease.yield_slots()`); it blocks while the lease is back in the queue. Then go on with the next step, with the same slots. Nothing has to be undone: a yield happens between steps. **If `slotfather yield` exits non-zero** (in-process: raises `SlotError`), the lease is gone (its holder was reaped, the queue removed) or the command did not run inside it: stop, and do not run further steps unleased. Exit 0 means the lease is held, whether or not it yielded.
4. **Never** yield in the middle of a step or a measurement (a measurement does not opt in), never kill or signal a process to make room, and do not start new work under the lease while yielding.

A client may ignore a request: the waiting request then waits as it would have, and the request is withdrawn once it is no longer needed.

**Mixed versions.** A slotfather before classes (`3e3a621` and earlier, Straylight's vendored copy) ignores them and the requests: its looks grant in arrival order, so until every client runs this version a waiting request may start as either order allows. It lists a yielded lease as a waiting request and may grant it again before the waiting request it yielded to; `slotfather yield` then returns as usual. Since the yield itself grants at once, the waiting request normally starts before an older client looks.
